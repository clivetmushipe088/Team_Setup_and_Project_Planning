1. Introduction and scope

The MoMo SMS Analytics system turns an XML export of MTN Mobile Money SMS messages into queryable, auditable transaction data. This document specifies the database that sits at the centre of it: the entity model, the schema as built, the rules that protect data quality, and evidence that all of it works.

The schema is implemented in database/database_setup.sql, a single idempotent script that drops and rebuilds the database, creates seven tables with their constraints, indexes, triggers and views, provisions two least-privilege accounts, and loads realistic seed data. It runs to completion with no errors and no warnings.

On the sample data. Twenty-five of the thirty-two seeded transactions are derived from the course dataset at data/raw/modified_sms_v2.xml: their amounts, dates, phone numbers, merchant till codes and SMS bodies are the values in that file, and the party names were extracted from the message text. The remaining seven are synthetic and marked as such in the script; they exist to cover the five categories the sample does not exercise (CASH_IN, CASH_OUT, BANK_DEPOSIT, UTILITY_PAYMENT, INTERNATIONAL_IN, REVERSAL) so that every category and every constraint keeps test coverage. No real customer data appears anywhere in this repository.

The schema was tested against that dataset, and an early version failed it. The first design keyed users on a mandatory, strictly formatted phone number. That schema could not store a single row of the course data: subscriber numbers arrive as 0789876543 rather than E.164, and roughly a third of the counterparties, merchant tills such as MTN:MoMoPay:Kigali_Mart and service endpoints such as MTN:Airtime, have no phone number at all. Section 3 explains the change that fixed it.

2. Entity Relationship Diagram

The two many-to-many relationships. users M:N transactions is resolved by transaction_participants, which qualifies every link with a role. transactions M:N tags is resolved by transaction_tags, whose composite primary key (transaction_id, tag_id) also carries the relationship's own attributes, confidence and tagged_by.

3. Design rationale

The design starts from one observation about the source data: a MoMo SMS does not describe a tidy pair of customers. An incoming transfer names a sender and a receiver; an airtime purchase names only the buyer; a bank deposit names an institution; a failed message may name nobody at all. Any schema that hard-codes sender_id and receiver_id onto the transaction row inherits that irregularity as a column full of NULLs.

So the central decision was to treat participation as a relationship in its own right. users and transactions stand in a genuine many-to-many relationship (a user takes part in many transactions, and a transaction involves several users) and transaction_participants resolves it, qualifying each link with a role. This removes the nullable-column problem, lets “everything user X did” run as one indexed query instead of a UNION of two, and leaves room to add a third role later without a migration. A second many-to-many relationship, between transactions and tags, is resolved by transaction_tags, whose composite primary key carries the relationship's own attributes: confidence and tagged_by belong to neither entity alone.

Categories live in a lookup table rather than an ENUM on the transaction, because a category carries its own attributes, a balance direction and a description, and because MTN adds product types without consulting our schema. Money is DECIMAL(15,2) and never FLOAT: a rounding error in a stored balance is a defect that compounds silently. system_logs.transaction_id is deliberately nullable, because a message that fails during parsing never becomes a transaction, and that failure is precisely the record an engineer needs.

The second decision came from testing the schema against the real dataset rather than reasoning about it. The first version keyed users on a mandatory phone number constrained to E.164, and it could not store a single row of the course data: subscriber numbers arrive in local 07… form, and about a third of the counterparties are merchant tills or service endpoints with no number at all. Keying the table on party_ref instead, a canonical identifier holding either the normalised MSISDN or the service code makes every party storable, while phone_number becomes a nullable attribute still validated whenever it is present. A BEFORE INSERT trigger rewrites 07… to +250… before the constraint is evaluated, so raw source values load unmodified and one subscriber cannot be stored twice under two spellings. The guarantee is kept and the data fits; the original design would have required discarding half of it.

Correctness is pushed down into the engine wherever it will go. A UNIQUE index on the SHA-256 of the message body makes re-running the ETL idempotent. CHECK constraints reject non-positive amounts and malformed phone numbers. Rules that span rows or need NOW(), namely no self-transfers, no future dates and mandatory audit of amount changes, are triggers, because a CHECK constraint cannot express them. A documented rule is a suggestion; an enforced rule is a guarantee.

RelationshipCard.Implemented by Reading

junction		 A transaction carries many tags; a tag is applied to many transactions.
transactions → system_logs 1 : Msystem_logs.transaction_id (nullable) One transaction has many log entries. A log entry may belong to none.

Why the participants junction, and not two columns. With sender_id and receiver_id on the transaction row, an airtime purchase leaves receiver_id NULL, a failed message leaves both NULL, and the question “show me everything user X did” becomes WHERE sender_id = X OR receiver_id = X, a predicate no single index can serve. The junction makes each participation one row, one index entry, one uniform query. Query 3 and Query 4 in section 9 demonstrate both directions.

6. Referential integrity and constraints

6.1 Foreign keys

The ON DELETE rule differs per relationship, and each choice is deliberate.

Child columnReferencesON DELETEON UPDATE
system_logs.transaction_idtransactions.transaction_idSET NULLCASCADE
transaction_participants.transaction_idtransactions.transaction_idCASCADECASCADE
transaction_participants.user_idusers.user_idRESTRICTCASCADE
transaction_tags.tag_idtags.tag_idCASCADECASCADE
transaction_tags.transaction_idtransactions.transaction_idCASCADECASCADE
transactions.category_idtransaction_categories.category_idRESTRICTCASCADE
  • RESTRICT on category and on user: financial history must never be orphaned. A category or a customer that has transacted cannot be deleted.
  • CASCADE on the junction rows: a participation row has no meaning without its transaction, so it goes when the transaction goes.
  • SET NULL on system_logs: deleting a transaction must not destroy the audit trail explaining what happened to it. The log survives with its pointer detached.

A conditional constraint is still a guarantee. chk_users_phone_format reads phone_number IS NULL OR phone_number REGEXP '^\+250[0-9]{9}$'. The IS NULL branch is not a loophole: it says that a party may have no phone number, a merchant till does not, while any number that is stored must be well formed. The alternative, relaxing the pattern to accept local 07… format as well, would genuinely weaken the rule, because the same subscriber could then be stored twice under two spellings and no index could tell that they were the same person.

Normalisation happens before validation rather than instead of it. trg_users_normalise_input rewrites 07… to +250…, and MySQL evaluates BEFORE INSERT triggers before CHECK constraints, so the constraint sees the canonical value. Raw source data loads unmodified and the strict rule still holds.

11. JSON data modelling and SQL → JSON mapping

The schemas and worked examples are in examples/json_schemas.json (JSON Schema draft-07). Every example in that file was generated by querying the live database, so the examples are genuine serialisations rather than hand-written approximations that drift from the schema. The complete mapping is in docs/sql_to_json_mapping.md; the essentials follow.

11.1 Type conversion

MySQLJSONRule and reason
DECIMAL(15,2)string Never a JSON number. IEEE-754 doubles cannot represent every two-decimal value exactly, and a rounding error in a stored balance compounds silently. "150000.00" round-trips exactly.
DATETIMEstring ISO-8601 with an explicit offset. MySQL DATETIME stores no timezone, so the API attaches Africa/Kigali: 2026-01-12T13:30:00+02:00.
ENUMstring Constrained by a JSON Schema enum with identical members.
BOOLEANtrue/falsen/a
NULLnull Typed ["<type>","null"] rather than omitted, so a client can tell “absent from the SMS” from “not requested”.

11.2 Structural rules

  • Foreign keys become objects, not ids. category_id never appears in a response; the nested category object replaces it, so a client renders a transaction from one request.
  • Junction tables disappear. Neither junction is a top-level resource. They become the nested participants and tags arrays, and the attributes stored on the relationship travel inside those items: role, confidence, tagged_by.
  • Composite keys dissolve. In transaction_tags, transaction_id becomes implicit (it is the parent) and tag_id sits on the item. The composite key has no JSON counterpart.
  • Derived fields are computed at the boundary. amounts.total is amount + fee, computed on serialisation rather than stored, so the two cannot drift apart.

The point worth dwelling on. confidence belongs to neither the transaction nor the tag. It exists only because the two are linked. That is exactly why the relationship needs its own table in SQL, and its own position in the JSON.

11.4 Privacy in the serialisation layer

Public responses carry masked phone numbers taken from v_transaction_summary; national_id, raw_sms_body and sms_hash are omitted entirely. The masking is produced by the database view, not by application code, an endpoint cannot leak a number it was never served.

Inside participants[] the displayable identifier is called masked_ref rather than phone_number, because for a merchant till it holds a code:

{ "role": "sender",   "party_ref": "+250789876543",
  "masked_ref": "+250789****543",          "has_msisdn": true  }

{ "role": "receiver", "party_ref": "MTN:MoMoPay:Kigali_Mart",
  "masked_ref": "MTN:MoMoPay:Kigali_Mart", "has_msisdn": false }

Two decisions are worth stating. A field whose name lies about its contents is worse than a slightly longer name, and the naming matches the sender_ref_masked / receiver_ref_masked columns of the view, so the API and the database agree on what an unprivileged caller may see. And a till code is not personal data, it identifies a shop, not a person , so falling back to it is safe rather than a leak.

12. The dashboard, and why there is no frontend code

This repository contains no hand-written HTML, CSS or JavaScript. That is a decision rather than an omission.

The Week 1 scaffold shipped an index.html, a chart_handler.js and a styles.css, 824 bytes between them, none of it doing anything beyond a console.log. Three languages and three files to maintain, for a page that could not render until the database existed. Alongside them sat three shell scripts, each a two-line wrapper around a single python3 command, one of which pointed at a file that does not exist.

All six were removed. The dashboard is instead generated, on the same principle as the ERD in section 2 and the JSON examples in section 11:

database  -->  scripts/build/make_dashboard.py  -->  data/processed/dashboard.html

One self-contained HTML file with its CSS and chart data inlined, written by a Python script that queries the database directly. Three consequences follow:

  • The source stays Python and SQL. Nothing in another language is maintained by hand, so nothing has to be kept in sync with the schema.
  • It cannot go stale. Regenerating produces output that matches the current schema by construction, the same property that makes the data dictionary in section 5 trustworthy.
  • No web server is needed. A single file opens directly in a browser.

Committing generated HTML would put HTML back into the repository language statistics and misrepresent what the project is written in, so .gitattributes marks generated artefacts linguist-generated and the course dataset linguist-vendored.

Status. The dashboard is not built yet. It follows the ETL, because there is no value in rendering a chart that has nothing to plot. The schema, the views that feed it (v_daily_summary, v_category_totals) and the JSON contract it will consume are all in place.

13. Reproducing this build

# 1. Build the schema and load the seed data
mysql -u root -p < database/database_setup.sql

# 2. Run the sample queries
mysql -u root -p --table < database/sample_queries.sql

# 3. Run the CRUD tests (restores the baseline when it finishes)
mysql -u root -p --table < database/crud_tests.sql

# 4. Run the security rule tests
#    --force is REQUIRED: every numbered statement is designed to fail, and
#    without it the client stops at the first rejection.
mysql -u root -p --table --force < database/security_rules_demo.sql

# 5. Prove the least-privilege grants are enforced, not merely declared
mysql -u momo_app -p -e "USE momo_sms_db; DELETE FROM transactions WHERE transaction_id=1;"
mysql -u momo_readonly -p -e "USE momo_sms_db; SELECT phone_number FROM users LIMIT 1;"

On credentials. The passwords in section 6 of database_setup.sql are development placeholders, committed only so the script is runnable as coursework. A real deployment reads them from the environment and never stores them in version control.
